REACT vs ANGULAR — FILES, PROJECT STRUCTURE AND COMMANDS
================================================================================
The React column describes this repository's actual frontend/ app
(React 19 + TypeScript + Vite 8 + Tailwind v4). The Angular column describes
what the equivalent app would look like using modern Angular (standalone
components + signals). Line counts and paths on the React side are real.


--------------------------------------------------------------------------------
1. PROJECT ROOT
--------------------------------------------------------------------------------

REACT (this repo)                     ANGULAR (equivalent)
-----------------                     --------------------
frontend/                             frontend/
  index.html          <- entry HTML     src/index.html
  package.json                          package.json
  vite.config.ts      <- build+proxy    angular.json     <- build/serve/test config
  tsconfig.json       <- project refs    tsconfig.json
  tsconfig.app.json                     tsconfig.app.json
  tsconfig.node.json                    tsconfig.spec.json
  public/             <- static assets  public/
  src/                                  src/

Key difference:
  Vite keeps build config in ONE small file you edit directly (vite.config.ts,
  ~20 lines here: React plugin, Tailwind plugin, and proxies for /api and
  /storage).
  Angular keeps it in angular.json, a large generated JSON describing named
  build targets (build / serve / test), file replacements per environment, and
  asset globs. You mostly change it through `ng` commands rather than by hand.

FILE-COUNT NOTE
  React: one component = one .tsx file. 60 files total.
  Angular: one component traditionally = 3-4 files
           (.component.ts / .component.html / .component.css / .component.spec.ts)
           so the same app lands nearer 150-200 files.
           Modern Angular can inline template+styles to cut this down.

4. ROUTING — SIDE BY SIDE
--------------------------------------------------------------------------------

REACT — routes are components, declared as JSX (see src/App.tsx):

  <Routes>
    <Route element={<Layout />}>
      <Route path="/" element={<LandingPage />} />
      <Route path="/events/:id/seats" element={<SeatBookingPage />} />
      <Route element={<Protected />}>
        <Route path="/orders" element={<OrdersPage />} />
      </Route>
    </Route>
  </Routes>

  - Guards are just components that render <Navigate> or an <Outlet>.
  - Params: const { id } = useParams()
  - Lazy loading, as actually written in src/components/seats/SeatViewer.tsx:

        const Venue3DLazy = lazy(() =>
          import('./Venue3D').then((m) => ({ default: m.Venue3D })))

    The .then() is not optional: React.lazy resolves to a module whose DEFAULT
    export is the component, and Venue3D is a named export, so it has to be
    remapped. Angular's loadComponent takes the named export directly.

ANGULAR — routes are a data structure:

  export const routes: Routes = [
    { path: '', component: LayoutComponent, children: [
      { path: '', component: LandingComponent },
      { path: 'events/:id/seats', component: SeatBookingComponent },
      { path: 'orders', component: OrdersComponent, canActivate: [authGuard] },
    ]},
  ];

  - Guards are functions returning boolean | UrlTree.
  - Lazy loading: loadComponent: () => import('./venue3d').then(m => m.Venue3D)
  - Params: inject(ActivatedRoute).snapshot.paramMap.get('id')

--------------------------------------------------------------------------------
6. GENERATION: THE BIGGEST DAY-TO-DAY DIFFERENCE
--------------------------------------------------------------------------------

ANGULAR
  ng generate component seats/seat-map

  creates, and registers where needed:
    seat-map.component.ts
    seat-map.component.html
    seat-map.component.css
    seat-map.component.spec.ts

REACT
  There is no generator. You create SeatMap.tsx yourself and export a function.
  Nothing to register anywhere; you import it where you use it.

  Consequence: React project structure is a team convention, not a rule.
  This repo's convention is:
      components/<domain>/  reusable UI
      pages/<domain>/       route-level screens
      lib/                  framework-free helpers (no React imports)
      context/              cross-cutting state
      types/                shared interfaces
  Nothing enforces it. In Angular the CLI enforces a shape for you.


--------------------------------------------------------------------------------
7. STATE AND DEPENDENCY INJECTION
--------------------------------------------------------------------------------

REACT (this repo)
  - Auth lives in context/AuthContext.tsx, provided at the app root and read
    with a useAuth() hook.
  - Everything else is local useState in the page that needs it.
  - lib/api.ts is a plain module; components import it directly.
  - No DI container. Swapping the API layer in a test means module mocking.

ANGULAR
  - AuthService is @Injectable({ providedIn: 'root' }) and injected into any
    component or other service that asks for it.
  - HttpClient is injected the same way, with interceptors for the JWT header.
  - DI makes substitution trivial: provide a fake in the test module.
  - Cost: you must understand injectors and provider scope.


--------------------------------------------------------------------------------
8. WHEN TO PREFER WHICH
--------------------------------------------------------------------------------

PREFER REACT WHEN
  - You need a specific ecosystem library. This app uses @react-three/fiber for
    the 3D venue; that binding is the most mature 3D integration available.
  - The app is small enough that framework ceremony would outweigh its benefit.
  - You want the freedom to assemble your own stack.

PREFER ANGULAR WHEN
  - A large or rotating team benefits from one enforced way of doing things.
  - Heavy forms: Reactive Forms with built-in validation beats hand-rolling.
  - Long-lived product: `ng update` migrating your code across major versions is
    a genuine maintenance advantage.
  - You want routing, HTTP, DI, forms and testing decided for you on day one.

HONEST TRADE-OFF
  React's flexibility is also its cost. This repo had to decide on routing,
  auth storage, data fetching and a design-token strategy, and had to hand-roll
  memoisation. Angular would have supplied answers to all of those, at the price
  of more concepts up front and roughly three times as many files.
